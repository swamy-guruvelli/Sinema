# Vercel for Beginners: From Code Change to Preview

Draft script for the approved visual direction. Target length: about 45-55 seconds. The characters remain unnamed on screen; the labels below are only production speaker labels.

## Scene 1 - The deployment problem

Visual: compact Vercel Docs browser panel. Keep the browser window partial, with the two characters on opposite sides.

**Skeptic:** I changed one button. Why does putting it online feel like a treasure hunt?

**Narrator:** Because code on your laptop still needs a build, a place to run, and a safe way to show your team.

**Skeptic:** So the app is finished, but nobody can see it?

**Narrator:** That is the deployment problem.

Beat labels: CODE CHANGE / HOW DOES IT GO LIVE? / DEPLOYMENT PROBLEM

## Scene 2 - The preview solution

Visual: animated three-step flow: GIT PUSH -> BUILD -> PREVIEW.

**Skeptic:** Then what does Vercel actually do?

**Narrator:** Connect your project, push a change, and Vercel builds a deployment you can open in a browser.

**Skeptic:** A preview before I touch the real site?

**Narrator:** Exactly. A Git change can create a shareable place to check the work.

Beat labels: PUSH THE CHANGE / VERCEL BUILDS IT / OPEN THE PREVIEW

## Scene 3 - From preview to production

Visual: light three-step flow: PREVIEW -> TEAM REVIEW -> PRODUCTION.

**Skeptic:** And when the team likes it?

**Narrator:** Review the preview, fix anything, then promote the ready change to production.

**Skeptic:** So preview is the practice stage?

**Narrator:** Yes. Local is for building, preview is for checking, and production is for everyone.

**Skeptic:** That is less scary than pressing deploy and praying.

**Narrator:** Vercel makes delivery repeatable. It does not replace good code.

Beat labels: SAFE TO CHECK / SHARE THE PREVIEW / PROMOTE WHEN READY
